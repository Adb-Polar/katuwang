1. Introduction & Purpose

This document is the finalized architecture baseline for Katuwang (Tagalog for “helper” / “partner”), a free, non-profit, web-based peer-tutoring management platform built for Taysan Resettlement Integrated School (TRIS), a Philippine public secondary school operating under classroom overcrowding and split shifts. It describes the system as actually built on the main branch, not the original thesis proposal.

1.1 Objectives

  • Give a single authoritative description of the runtime, logical, data, and security architecture.
  • Record the architectural style and the decisions that shaped it, with rationale.
  • Serve as the onboarding reference for developers and the evaluation artifact for the capstone defense.

1.2 Audience

Project developers and maintainers, the capstone advisory panel, and TRIS technical stakeholders responsible for future operation.

2. System Overview

Katuwang connects student tutors (peers who volunteer to teach) with student learners (peers who need help) so that tutoring can be organized, scheduled, assessed, and moderated instead of being ad hoc. Everything is voluntary and free — there is no payment or monetization anywhere in the system, and no upload/storage of learning materials because tutoring physically happens on school premises.

The platform is delivered as a single full-stack Next.js 16 application (App Router) backed by a MariaDB/MySQL database. It exposes three role-scoped portals from one deployable unit:

Role (Prisma Role)PortalCore capability
STUDENT_LEARNER/learnerBrowse/enroll in classes, get matched to tutors, post class requests, take pre/post-tests, view progress
STUDENT_TUTOR/tutorCreate/run classes & sessions, get certified per topic, fulfill class requests, build session tests
ADMIN/adminUser & class moderation, question bank, certification review, subjects/topics, settings, analytics, audit log

The system is scoped into six core modules: (1) User Management, (2) Session Management, (3) Tutor Matching, (4) Assessment, (5) Chatbot Assistant, and (6) Analytics Dashboard. All six are implemented; the chatbot is a deterministic rule-based intent matcher (no LLM), consistent with the thesis delimitation.

Scope note. The thesis proposal named a fourth “Teacher Moderator” role. It was intentionally cut — the platform ships with exactly three roles and moderation duties fold into ADMIN. See docs/reference/decisions.md.

3. Architectural Drivers

3.1 Quality Attributes (ranked)

#AttributeWhy it drives the architecture
1Privacy / ConfidentialityRA 10173 mandates double-blind anonymity between peers. Drives the anonymous-ID scheme, peer-facing DTO discipline, and an admin-gated real-name override.
2SecurityMinors' data. Drives edge RBAC + per-route re-checks, bcrypt hashing, JWT sessions, account lifecycle gating at login, and an immutable audit log.
3MaintainabilityStudent-built, must be handed over. Drives one language end-to-end (TypeScript), one ORM, lean Server Components, service logic in src/lib/, and Zod-validated boundaries.
4Correctness / IntegrityEnrollment caps, certification gates, request lifecycles. Drives Prisma transactions, compound unique constraints, and pure testable domain functions.
5Usability & AccessibilityLow-resource devices. Drives responsive DaisyUI/Tailwind layout, server rendering, and no heavy client frameworks.
6DeployabilityMinimal ops capacity at TRIS. Drives a single monolith, no background workers, no message broker, no external service hard-dependency.

3.2 Constraints

  • Regulatory: RA 10173 (Data Privacy Act) — parental/guardian consent captured at registration; peer identities never crossed.
  • Non-profit: no billing, payment, or monetization code anywhere.
  • No file storage: no upload endpoints or blob storage — tutoring materials are handled in person.
  • No scheduler/queue infrastructure: all work is request-driven; there is no cron, SSE, polling worker, or background job runner. Time-based notifications (e.g. “class starts in 1 h”) are therefore out of scope.
  • Chatbot: nav/FAQ/recommendation only, deterministic, no generative model, no new runtime dependency.
  • Analytics: descriptive aggregates only — no ML, prediction, or educational data mining.
  • Three roles only (see §2).

3.3 Assumptions

  • Single institution (TRIS); no multi-tenancy.
  • School-day-length engagement — JWT sessions expire after 8 hours.
  • SMTP is available for password-reset mail; when unset, the app logs the link to the console (dev fallback).
  • Modest concurrent load (hundreds of students), well within a single Node process + one MariaDB instance.

4. Architectural Style & Guiding Principles

Katuwang is a modular monolith built on the Next.js App Router, combining React Server Components (RSC) for data-fetching pages with client “islands” for interactivity, plus co-located REST route handlers for mutations.

PrincipleApplication in Katuwang
Server-authoritativeEvery privileged decision is re-checked on the server (getServerSession + role guard in each route handler). UI hiding is cosmetic only.
Lean pages, thick componentssrc/app/**/page.tsx are Server Components that fetch session + initial data; interaction/state lives in "use client" components under src/components/.
Domain logic is pure & centralizedRanking, grading, access rules, serialization, config resolution live as framework-free functions in src/lib/ and are unit-tested in isolation.
Validated boundariesAll request bodies parse through Zod schemas (src/lib/validations/); first validation error returns HTTP 400.
One ORM, one clientAll DB access goes through the singleton prisma (@/lib/prisma); multi-table writes are wrapped in prisma.$transaction.
Feature flags over branchesRuntime behavior toggled by PlatformSetting rows (e.g. matchingEnabled, chatbotEnabled) read through src/lib/settings.ts.
Privacy by constructionPeer-facing queries select only id + anonymousId (+ non-identifying fields); real names require an admin route or the explicit showTutorRealNames override.

6.1 Presentation Layer

Pages are Server Components by default: they call getServerSession(authOptions), load only the data the first paint needs, and pass it as props into client components. Client components own forms, modals, tables with client-side sort/filter, and optimistic UI. The shared PortalLayout provides the role-aware sidebar, top-bar global search (⌘K), and the notification bell.

6.2 API / Route-Handler Layer

Each mutation or protected read is a route handler under src/app/api/. The canonical shape is: authenticate → authorize by role → Zod-parse → execute (often inside a transaction) → return payload or { error }. Server errors are logged with console.error and returned as a generic 500 so internals never leak.

6.3 Domain & Service Layer

Business rules live here as framework-free modules so they can be reasoned about and unit-tested without HTTP or a database. Examples: rankMatches() scores classes for a learner using explicit tunable weights (topic overlap, certified-topic bonus, schedule fit, grade proximity, soonness tiebreak); gradeAttempt grades an assessment; sessionTestAccess decides whether a learner may open a PRE or POST attempt given the session lifecycle.

6.4 Data-Access Layer

A single Prisma client instance is reused across hot reloads via a globalThis guard. All dependent multi-row writes (e.g. tutor registration creating User + TutorProfile; accepting a class request creating a TutorClass and transitioning the request) are wrapped in prisma.$transaction for atomicity.

6.5 Persistence Layer

MariaDB via the Prisma MariaDB adapter. Status fields use Prisma enums for integrity; the subject taxonomy moved from a compile-time enum to admin-editable Subject/Topic tables, with subject columns storing the immutable slug as a plain string.

7.2 Cross-Module Dependencies

  • Matching → Session Management: rankMatches reads live TutorClass + ClassSession + enrollment counts; accepting a TopicRequest creates a TutorClass.
  • Matching → Assessment: ranking gives a bonus for topics the teaching tutor holds a CERTIFIED TopicCertification for.
  • Assessment (session tests) → Question Bank: session-test questions are drawn from AssessmentQuestion filtered to origin: BANK plus the tutor's own origin: TUTOR questions; the tutor certification quiz pool is bank-only.
  • Chatbot → Matching: the learner “recommend” intent calls the same rankMatches engine.
  • All modules → Notifications & Audit: lifecycle events emit Notification rows; every admin moderation action writes an AuditLog row.
  • All modules → Settings: matchingEnabled, chatbotEnabled, sessionTestsEnabled, requireRegistrationApproval, requireCertificationForClassCreation, autoCertifyOnAssessmentPass, registrationOpen, showTutorRealNames gate behavior at runtime.

8. Runtime Views (Key Scenarios)

8.1 Registration (learner or tutor)

  1. Client form (LearnerRegisterForm / TutorRegisterForm) does local validation, then POST /api/register with a type discriminator.
  2. Route handler Zod-validates, enforces guardian consentGiven, checks e-mail uniqueness (409 on conflict).
  3. bcrypt.hash(password, 12); generateAnonymousId("LEARNER"|"TUTOR") atomically increments the IdCounter row (STU-#### / TUT-####).
  4. prisma.$transaction creates User (+ TutorProfile for tutors). If requireRegistrationApproval is on, status is PENDING; otherwise ACTIVE.
  5. 201 with the new anonymous ID; client redirects to /login (or /pending-approval).

8.2 Authentication & RBAC Enforcement

  1. signIn("credentials", …) → NextAuth authorize() in src/lib/auth.ts.
  2. Look up user by e-mail, bcrypt.compare the password.
  3. Account-status gate: expired SUSPENDED auto-reactivates; active SUSPENDED/BANNED rejected; PENDING/DECLINED return sentinel errors that the login page maps to /pending-approval / /account-declined.
  4. On success, jwt callback embeds id, anonymousId, role, fullName; session strategy is JWT, maxAge 8 h.
  5. Every subsequent protected request passes through src/proxy.ts: valid token required, then path-prefix → role check (/admin→ADMIN, etc.), redirect to /unauthorized on mismatch.
  6. The target route handler independently re-runs getServerSession + role check (defense in depth).

8.3 Tutor Matching

  1. Learner submits MatchCriteria (subject slug, topics, grade, preferred time slots, class format) to POST /api/learner/match.
  2. Handler checks matchingEnabled, loads candidate published SCHEDULED classes in the subject with sessions, enrollment counts, and the teaching tutor's certified topics.
  3. rankMatches() scores each: +10 per matched topic, +5 per certified matched topic, +3 per session landing in a preferred slot, +6/+3/+2 for exact/adjacent/any grade, up to +2 soonness tiebreak; full-classes excluded.
  4. Ranked results with human-readable MatchReasons return to the learner. If nothing scores well, the UI routes the learner to post a class request (TopicRequest), optionally directed at one tutor.
  5. A tutor accepts an open request → POST /api/tutor/topic-requests/[id]/accept transactionally creates a TutorClass and moves the request OPEN → ACCEPTED; enroll/unenroll and class status changes drive it through ENROLLED → FULFILLED (or re-open). Each transition emits notifications.

8.4 Tutor Certification Assessment

  1. Tutor requests certification for a (subject, topic) → TopicCertification row (PENDING).
  2. Tutor starts a quiz: assessmentPicker.pickQuestionIds() selects N bank questions (origin: BANK) per the global getAssessmentConfig() (question count, pass %, min bank size).
  3. AssessmentAttempt + AssessmentAttemptItem rows track the run; on submit, gradeAttempt computes scorePercent and sets PASSED/FAILED.
  4. If autoCertifyOnAssessmentPass is on, a pass flips the certification to CERTIFIED; otherwise an admin reviews at /admin/certifications (CERTIFIED/REJECTED + note). Result notification is emitted.
  5. Tutors may raise a QuestionRequest asking an admin to add bank questions for a thin topic.

8.5 Session Pre-/Post-Test (learner progress)

  1. Tutor builds one SessionTest per ClassSession (unique) from bank + self-authored questions; publishing sets PUBLISHED.
  2. Learner takes the same question set twice: a PRE attempt opens once the test is published; the POST attempt opens automatically when the tutor marks that session COMPLETED (kind lives on SessionTestAttempt, not the test).
  3. sessionTestAccess authorizes each attempt against the session lifecycle; sessionTestResults computes per-question and per-learner PRE→POST deltas.
  4. Results feed the tutor's charts, the learner's /learner/progress, and the admin read-only views. Diagnostic only — no pass/fail. sessionTestsEnabled is the kill switch.

9.2 Normalization & Denormalization

  • 3NF for the core. One-to-many child tables (ClassTopic, ClassSession, TopicRequestTopic, TopicRequestSlot, option/item tables) rather than JSON blobs or repeating columns.
  • Deliberate denormalization of topic. Topics are plain strings on ~7 child tables, not foreign keys to Topic. Topic is the editable catalogue and validation source (topicExists()); renaming a topic fans the new string out to all denormalized columns inside one transaction. Rationale: the app never had DB-level referential integrity on subject/topic, and a full FK rewrite carried a far larger blast radius for no operational gain (decision B in subject-topic-management.md).
  • Compound unique constraints enforce business rules at the DB (e.g. one enrollment per (classId, learnerId), one SessionTest per sessionId, one certification per (tutorProfileId, subject, topic)).
  • Enum-backed status columns (AccountStatus, ClassStatus, TopicRequestStatus, AssessmentAttemptStatus, SessionTestStatus, …) keep lifecycle state valid without a lookup table.

9.3 Anonymous Identity Generation

generateAnonymousId(role) performs an atomic prisma.idCounter.update({ data: { count: { increment: 1 } } }) — the increment is executed by the database, so concurrent registrations cannot collide — then zero-pads to TUT-0001 / STU-0001. The same pattern (generateClassCode) issues C-0001 class codes, upserting the counter row so it works on a fresh database.

10. Security & Privacy Architecture

10.1 Authentication

  • NextAuth Credentials provider; passwords stored only as bcrypt hashes (cost 12).
  • Stateless JWT sessions signed with NEXTAUTH_SECRET, 8-hour expiry, carried in an HTTP-only cookie.
  • Password reset: single-use, hashed, expiring PasswordResetToken; link delivered by SMTP (src/lib/mail.ts), console fallback when SMTP is unset.

10.2 Authorization

  • Layer 1 — edge middleware (src/proxy.ts): authenticated + path-prefix → role match for /dashboard, /admin, /tutor, /learner.
  • Layer 2 — route handler: every API route re-derives the session with getServerSession(authOptions) and checks session.user.role, returning 401/403 on failure. UI affordances are never the control.
  • Resource-scoped checks: handlers verify ownership (e.g. a tutor may only edit their own class, a learner may only open their own attempt) via sessionTestAccess, topicRequestVisibility, and explicit where clauses.

10.3 Double-Blind Anonymity (RA 10173)

Core non-negotiable constraint. Learners and tutors must never see each other's real name, e-mail, or contact info across the peer boundary.

  • Every student receives a sequential anonymous ID at registration; peer-facing UI and API responses expose only id + anonymousId plus non-identifying attributes (grade level, section).
  • Peer-facing Prisma queries use explicit select to exclude firstName/lastName/email.
  • Admins can see real identities (required for moderation). The showTutorRealNames platform setting is an explicit, admin-gated, default-off override — not a normal code path.
  • Real name / e-mail changes require an admin route; grade level + section are self-service because they are not identity anchors.

10.4 Account Lifecycle

AccountStatus: ACTIVE, SUSPENDED (optionally time-boxed via statusExpiresAt, auto-reactivated at next login), BANNED, PENDING (awaiting approval, cannot log in), DECLINED (registration rejected, reason surfaced on /account-declined). Classes have a parallel lifecycle (ClassStatus) with a tutor ClassAppeal path that notifies admins.

10.5 Auditability

Every admin moderation action (suspend/ban user, moderate class, review certification, resolve request, edit settings) writes an AuditLog row (adminId, action, targetType, targetId, reason, timestamp) through src/lib/auditLog.ts, surfaced read-only at /admin/audit-log.

14. Architecture Decision Record (Summary)

Full rationale lives in docs/reference/decisions.md and the per-feature plans under docs/plans/. The decisions that shaped this architecture:

#DecisionRationale
ADR-1Modular monolith on Next.js App Router, not a separate SPA + APIOne language, one deploy, minimal ops for a school with little technical capacity; RSC removes most client data-fetching code.
ADR-2Three roles only; “Teacher Moderator” droppedOwner decision (2026-09-03). Moderation folds into ADMIN; avoids a fourth portal and guard set.
ADR-3JWT session strategy (no DB session table)Stateless app tier; school-day (8 h) lifetime; no session store to operate.
ADR-4Two-layer RBAC (edge middleware + per-route re-check)Defense in depth; middleware is coarse and fast, route handlers own resource-level authorization.
ADR-5Anonymous IDs via atomic IdCounter incrementRace-free sequential IDs (TUT-/STU-/C-) without a UUID's opacity cost to users; satisfies RA 10173 double-blind.
ADR-6Subjects/topics: catalogue tables + denormalized string columns (Path B)Admin-editable taxonomy with a small blast radius; no FK migration; slug stays equal to the old enum value (lossless cast).
ADR-7Global assessment config, not per-(subject, topic)One PlatformSetting-backed set (question count, pass %, min bank size); the per-topic config table was removed.
ADR-8Session pre/post-test scoped per ClassSession, one question set served twice (kind on the attempt)Per-session granularity makes score change attributable to that session's material; identical question set makes per-question PRE→POST deltas meaningful.
ADR-9Chatbot is deterministic intent matching, no LLMMatches the thesis delimitation (“no free-form generative chat”); zero new runtime dependency; misses logged to ChatbotMiss to grow the FAQ.
ADR-10No scheduler / queue / real-time transportKeeps the deployment a single process; all work is request-driven; time-based reminders are explicitly out of scope.
ADR-11No file upload / storageTutoring happens on school premises; removes a whole class of storage, quota, and moderation concerns.
ADR-12Domain logic as pure modules in src/lib/Unit-testable without HTTP/DB; keeps route handlers thin and readable.
